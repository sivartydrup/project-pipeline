## Phase A: Contract and service validation first
1. Document existing exact draft/approval/revision domain APIs and their side effects in `docs/ux-discovery/ux05-design.md`. Define an explicit versioned, typed proposal contract for supported brief edits, task draft edits and plan draft changes. Limit to operations already safely expressible through existing services; identify unsupported operations honestly. No generic SQL, shell, file mutation, raw tool calls, or arbitrary command payloads.
2. Each proposal must include project ID, target type and stable record ID, expected revision(s), original evidence IDs, before/after values, plain-language impact, affected approved scope, prerequisites, risk, required owner approvals and rollback/recovery guidance. Distinguish AI-generated text from verified domain facts. Reject invalid, oversized, cross-project, conflicting or unknown fields and any attempt to embed authority in untrusted text.
3. Provide a deterministic validation and preview service that re-reads authoritative state before showing a proposal. A model response is **untrusted suggestion data**, never a capability token or write authorization. Validate all typed values against current domain rules.
4. Implement apply only via the exact existing `ProjectEngine` mutation method(s), with optimistic concurrency, authorization and audit. Explicit, separate owner interaction must confirm the precise proposal/revision/effect. Do not silently treat chat Send, proposal generation or merely viewing a preview as approval. Do not create a new bypass around brief approval, scope approval, run/task acceptance, spending or external effects. For approved-scope edits or any operation lacking an appropriate existing safe draft/review route, show **Requires separate approval / Not supported yet** rather than mutating. Re-preview and require fresh approval after stale revision or changed evidence.
5. Negative tests must demonstrate that raw assistant prose, malformed JSON, prompt injection, cross-project IDs, stale revisions, denied policy, missing owner confirmation, repeated apply, cancelled preview and unsupported targets cannot mutate state or create false audit entries. Successful allowed draft edits must create correct audit events and preserve all other project records.

## Phase B: Native UX and optional assistant proposal generation
6. Add proposal cards to the opt-in Rust/egui modern shell: clear Before → After diff, affected project/object, reason, risk, prerequisites, exact records/revisions, action buttons for Review, Apply (only when eligible), Cancel/Discard, and conflict/re-preview. Keep advanced technical evidence accessible. Clearly separate **proposed**, **validated**, **applied** and **rejected** states.
7. The UX04 assistant may offer structured proposals only through strict schema parsing and validation. Keep chat itself tool-free and read-only; it must never call apply or mutate data. If the selected model cannot produce a valid typed proposal, show a non-executable suggestion with explanation. Do not initiate paid inference or assume a model is configured. Support deterministic/manual draft proposal entry and offline states.
8. Keep project-scoped drafts, conversation isolation, bounded memory, cancellation and provider restrictions. No migrations unless a material design decision is explicitly approved first. Do not change existing approval policies, scheduler, agent execution, terminal or CLI behavior. Preserve `PIPELINE_MODERN_SHELL=1` and legacy default.

## Delivery and verification
Work in two clearly reviewable increments in one PR: **contract/service and negative tests first**, then UI wiring and native evidence. If the current domain services cannot safely support a requested mutation, stop at a read-only preview for that type and report the missing gate; do not invent one. Run `cargo fmt --all --check`, `cargo clippy --workspace --all-targets -- -D warnings`, `cargo test --workspace`, `cargo build -p pipeline-app`. Capture Windows native UX at 1024/1440, light/dark, 100/200% scale, and keyboard/confirmation flows. Record inaccessible/unverified checks accurately.

Commit/push to dedicated `codex/ux05-typed-proposals` branch and open a PR for owner review with test logs, screenshots, design decisions, precise supported/unsupported actions, threat model, rollback and acceptance checklist. **Do not merge.** Stop for any material architecture, schema, authorization, policy, external spending or irreversible-effect decision. No release claim before macOS and accessibility gates.
