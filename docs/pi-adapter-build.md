# P15 Pi RPC adapter

Started 10 October 2026 after [owner acceptance of P14](approval-p14-2026-10-10.md). Windows foundation verification completed 11 October 2026.

The first adapter slice adds byte-level LF-delimited JSON framing and request-ID response correlation. Fixtures cover partial reads splitting a UTF-8 character, Unicode line and paragraph separators within JSON strings, CRLF, truncated/invalid records, interleaved events, out-of-order responses, and response command mismatch. The [fixture log](evidence/p15-rpc-fixtures.log) and `cargo fmt --all -- --check` pass on Windows.

An installed global `pi` command is unavailable. A no-inference probe of `@earendil-works/pi-coding-agent` 1.1.0 via `npx` confirmed the RPC `get_state` response, using disabled tools, extensions, MCP, skills, context files, and offline mode. Its selected default model was paid, so P15 must require an explicit provider/model and a scoped one-use prompt approval before any model dispatch. This probe did not send a prompt.

The adapter now owns a Pi 1.1.0 RPC subprocess in the isolated checkout, requires an explicit provider/model, probes the exact executable version, correlates command responses while draining events, and binds a persistent Pi session ID to the run. A policy extension is loaded explicitly with project and user extensions, MCP, skills, and context files disabled. The extension pauses every model tool call for the application's existing action service. Local read/edit/write paths are checked against the checkout; shell commands create exact one-use owner requests. A separate hook stops at 30 provider requests before an additional request is sent, following the owner's revised approval. Run startup waits for a policy-gate handshake and fails closed on extension errors. The worker enforces the 15-minute wall and observed-token stops, records normalized events, retains interrupted checkouts, and captures the tracked diff when the agent submits. The Runs tab now selects OpenCode or Pi.

The [full Windows workspace test](evidence/p15-test.log), [Clippy](evidence/p15-clippy.log), and [app/CLI build](evidence/p15-build.log) pass after the store repair. A no-inference Pi 1.1.0 process probe verified startup, the extension UI approval subprotocol, abort, and reopening the persistent session. The approved [live run record](approval-p15-live-smoke-2026-10-10.md) uses a disposable addition project with an expected failing test. Its first pre-inference launch exposed an OpenCode-only session ID validation in the store; the store now validates Pi UUIDs and records the actual harness. The second launch reached an exact Pi shell request, which remained pending without owner action approval. The worker stopped at its 15-minute wall limit, retained the checkout, and closed the policy request. This run verifies the live policy pause and wall stop but not task completion. The [first launch log](evidence/p15-live-windows.log) and [second launch log](evidence/p15-live-windows-retry.log) are preserved.

The next approved 15-call run corrected `src/lib.rs` and executed `cargo test` through exact owner-approved shell actions. The model then requested two fabricated test logs and an environment dump containing its bridge token; those actions were denied. A real `cargo test` log was captured separately in the isolated checkout. The run reached its model-call cap before task submission; [its event log](evidence/p15-live-windows-third.log) and policy audit are retained. The owner approved a revised 30-call cap and one further free-model run. The task prompt now includes the exact PowerShell bridge call and payload shapes and explicitly forbids hand-written test results and environment dumps. This is a correction to the observed failure, not completed end-to-end evidence.

The 30-call North run fixed the source and captured a real [passing sample test log](evidence/p15-sample-test.log) (SHA-256 `b5632030bc9ded9e8b1e556400bc4f975032d56dd30300982736fe3ed86cba80`) and [source diff](evidence/p15-sample-diff.patch). Its [event log](evidence/p15-live-windows-final.log) shows the live bridge and policy flow, but the model confused the bridge reply's top-level project revision with `result.revision` for the task, used a filename instead of the returned artifact ID, and reached the cap without submitting. A relative CLI path in the headless launch was also identified and corrected to an absolute path; the disposable run used a checkout-local CLI copy before that source fix was built. Repeated identical Pi UI requests now have distinct one-use policy digests, so a consumed approval cannot silently deny a fresh proposal. The prompt explicitly distinguishes `result.revision` and `result.id`. Full workspace tests, Clippy, format check, and build pass after these fixes.

The next approved [Laguna run](evidence/p15-live-windows-laguna.log) used the free route recorded in [the route check](evidence/p15-laguna-route.log). It repaired the source, ran the real test successfully, and attached the passing test log as artifact `600d1cca-5a6e-489a-9d32-bd27b9f7acfd` with SHA-256 `79c9576e32ddb89a6ec8e2f4ab9cc3ea5f816cd78bc3922525ea459221b575db`. The model then omitted `log_artifact_id` from `test.record`, retried with it nested inside `environment`, and reached the 30-call stop. The bridge rejected both malformed test records. The task was not submitted. The prompt now gives a concrete four-field `test.record` JSON example and tells Pi to use its PowerShell tool for bridge commands. The focused engine tests and format check pass after this correction.

A further approved [Laguna retry](evidence/p15-live-windows-laguna-rerun.log) started with the correct PowerShell bridge call, fixed the source, and passed the real test. Pi then exhausted upstream retries on HTTP 429 before artifact attachment. The adapter now reports the HTTP status from `auto_retry_end` without exposing the provider's response body. This is an external free-endpoint failure, and the run did not submit the task.

The separately approved [Nemotron run](evidence/p15-live-windows-nemotron.log) completed the Windows journey. It fixed only `src/lib.rs`, ran the real [passing test](evidence/p15-nemotron-sample-test.log), attached that log with verified SHA-256 `b36506acce90cccb0a42ecb8aabc7e2ef74bd506cd31d37c1af25b8f49c89ea1`, recorded the passing `cargo test` result, and submitted task `fix-add` through the scoped bridge after exact owner approval for each shell action. The first log attachment reported a hash mismatch despite matching independent hashes; a fresh one-use retry succeeded with the same file and digest. No mismatch was bypassed. The app captured the tracked [source diff](evidence/0c5c98e7-6068-4c41-9233-276844cc0c69.patch). Persisted run `0c5c98e7-6068-4c41-9233-276844cc0c69` is `completed`; the disposable task is in `review`, pending its own owner acceptance. This satisfies P15's end-to-end Windows task-run check without claiming that the sample task was accepted. Final Windows [workspace tests](evidence/p15-final-test.log), [Clippy](evidence/p15-final-clippy.log), format check, and [app/CLI build](evidence/p15-final-build.log) pass. The M1 Max task journey remains a pre-release check.
